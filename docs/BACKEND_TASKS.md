### B01. Цельные выдержки из описаний

**Доказательство:** `backend/matching.py:106–113` строит произвольные окна слов. Для HK-31819: Алматы / Лайв-бэнд / корпоратив / 2026-10-16 / 1 150 000 ₸ / язык и часы null. Выдержка начинается хвостом «расширенного состава», включает другой, большой состав и заканчивается «Репертуар: от».

**Сделать:** выбирать законченный смысловой блок; сохранять название состава, к которому относится факт. При длинном описании искать содержательный фрагмент и после первых 260 символов, сохраняя исходный контекст. Не переписывать CSV и не приписывать базовой цене включение расширенного состава.

**Готово:** дословная выдержка до 260 символов читается самостоятельно, не начинается хвостом фразы и не обрывает смысл; этот пример и прежние случаи длинных описаний закреплены проверками. Фильтры и порядок карточек остаются прежними. Если корректного короткого блока нет — использовать честный вариант B02.

### B02. Конкретное объяснение при отсутствии содержательного описания

**Доказательство:** `backend/matching.py:143–175`; HK-25279 на Алматы / Лайв-бэнд / корпоратив / 2026-10-17 / 1 500 000 ₸ / optional null цитирует «мы действительно сверкаем — звуком, энергией и атмосферой». Это не отличительный факт. В структурированных полях есть русский язык и максимум 5 часов.

**Сделать:** когда описание не содержит надёжного предметного факта, составлять 1–2 предложения из доступных сведений о профиле и соответствии запросу. Исходный фрагмент сохранять отдельно для просмотра. Не придумывать репертуар, состав, отзывы, рейтинг, итоговую цену или подтверждённую бронь.

**Готово:** этот профиль объясняется проверяемыми сведениями; рекламная цитата не выдаётся за основание выбора. Когда сами исходные сведения у двух профилей совпадают, ограничение данных признаётся явно — искусственную уникальность не сочиняем. Сохраняются схема API и честный deterministic-режим.

### B05. Честная диагностика запуска

**Доказательство:** `backend/app.py:114` при отсутствии UI всегда пишет «API доступен», даже если CSV тоже не загрузился. `backend/app.py:36` оставляет в журнале только класс ошибки.

**Сделать:** разделить сообщения «нет интерфейса» и «недоступен каталог»; дать оператору локальную причину ошибки загрузки. HTTP-ответ сохраняет понятный 503 без внутренних путей и traceback.

**Готово:** отдельно рассмотрены отсутствие CSV, неправильный CSV, отсутствие frontend и их сочетание; сообщение не утверждает доступность неработающего API. Обычный запуск не меняется.

### B06. Короткий smoke должен замечать исчезновение советов

**Доказательство:** `scripts/smoke.py:43` перебирает suggestions, поэтому пустой массив не вызывает ошибки. Совет смены даты этот короткий скрипт отдельно не требует. Полный браузерный прогон уже проверяет больше; задача улучшает быстрый сигнал между публикациями.

**Сделать:** для бюджета 1 ₸ требовать подходящий совет бюджета; для занятого флориста Астаны 15 октября — совет даты. Повторить предложенные запросы через HTTP, проверить положительный результат, ровно одно изменённое поле и версию данных. Не привязывать общую логику к случайному top-3.

**Готово:** искусственное исчезновение любого ожидаемого совета не даёт PASS; неизменённая рабочая реализация проходит. Инструкции запуска обновлены по факту.

### B07. Идентификация работающего релиза

**Доказательство:** health сообщает версию схемы API и число профилей, но два разных серверных процесса с 66 строками выглядят одинаково.

**Сделать при наличии времени:** добавить необязательные диагностические dataset_version и build/release id, сверяемые с отчётом. Идентификатор должен передаваться воспроизводимо; Git не становится обязательной зависимостью запуска экспертом. Не выдавать произвольную строку окружения за доказательство проверенного SHA.

**Готово:** по диагностике можно отличить актуальный сервер от старого процесса; API v1 и обычный запуск без специальной настройки работают. Не перегружать карточки пользователя техническими версиями.

### B08. Бюджет: принятое решение для текущего v1

Backend принимает положительный JSON integer без бизнес-потолка; браузер использует точные целые JavaScript, до 9 007 199 254 740 991 включительно. На текущем наборе все цены намного меньше границы, основной сценарий не ломается.

Сохраняем существующее поведение и явно документируем разницу в API_CONTRACT. Не добавляем неожиданное серверное ограничение и не меняем тест на большой integer только ради одинаковых типов. Если появится реальная потребность в суммах вне браузерного диапазона — отдельно согласовать точный строковый формат следующей версии. Для сдачи это не новая функция и не приоритетная ошибка.

### B09. Вес пересекающихся основ

**Доказательство:** `backend/matching.py:59–68`; слово «ведущий» совпадает с «ведущ» и «веду» и получает два балла. Это ограничение выбранной эвристики, не нарушение жёстких фильтров или стабильности.

**Сделать только после основного:** убрать повторный вес одного свидетельства и описать правило. ## 4. Как принимаем полезное из обеих веток

1. Единственный публикующий общую сборку — наш интегратор. Друг продолжает dev-zoro; его рабочие файлы, коммиты и ветку не меняем.
2. Получаем новые remote refs и сравниваем коммиты от общей базы, а не заменяем каталог старым деревом друга. На первом срезе 4a9d305 был старше общей версии; затем друг получил её и опубликовал e8bf9c2. Поэтому прямой diff старого и нового tip включает также уже общий backend. Отделяем новые изменения друга от пришедшей к нему общей истории.
3. Берём готовые изменения, соответствующие ТЗ, с конкретными подтверждаемыми фактами, совместимым API и воспроизводимым запуском. Дизайн оценивает друг; backend-альтернативы сравниваем по соблюдению ограничений, качеству результата, понятности и стоимости зависимостей. Более новый файл автоматически не означает лучший.
4. Если друг изменил backend, читаем его diff и пересечение с нашими правками. Полезную функцию адаптируем в candidate/нашей ветке, сохраняем авторство; конфликты решаем по поведению, без массового выбора ours/theirs. При неоднозначном продуктовом выборе готовим конкретные варианты для участника.
5. От общей актуальной истории создаём отдельный candidate, обычными merge включаем точные SHA нашей и его частей. Проверяем именно этот код с реальным API и UI, затем публикуем один проверенный SHA в integration и main и сверяем remote.
6. Возвращаем общую версию в dev-dinmukhammed. Друг получает её сам в dev-zoro. Подробные команды, правила конкурентного push и отчётность — в общем промпте и RELEASE_SCHEDULE.

## 6. Идеи с практической пользой

Уже есть две полезные добавки команды: сравнимые факты карточек и рассчитанные альтернативы даты/бюджета. Дорабатываем их качество. В [обсуждении выбора площадок на Reddit](https://www.reddit.com/r/weddingplanning/comments/1gjs3ip/first_day_of_some_light_window_shopping_for_a/) участники описывают неудобство скрытых цен и доступности; это частные отзывы, а не исследование рынка. Вывод для нас: показывать цену «от», понятный календарный статус и что реально известно об услуге. Такие сведения уже поддерживаются нашим сценарием.

Новые рейтинги, состав цены, вместимость и отзывы нельзя выдумывать из отсутствующих полей. Кабинеты, платежи, бронь, уведомления и отдельная БД не нужны для текущего ТЗ. Семантический поиск/LLM — возможный последующий эксперимент с измеримым улучшением; пока фактический runtime детерминированный и так описан. Внешняя модель ради вывески добавляет зависимости и не закрывает найденные ошибки сама по себе.
