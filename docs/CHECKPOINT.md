# Личный checkpoint без таймера

`scripts/checkpoint.py` — однократный gate для собственной ветки. По умолчанию он проверяет изменения. Явный `--publish` разрешает создать один осмысленный commit и отправить **только личную ветку**. Он не публикует `main`/`integration`, не выполняет merge/rebase/reset/force-push и не создаёт второй таймер. Единственный heartbeat интегратора сохраняется.

## Запуск

Из корня своей копии, в `.venv` с установленными `requirements.txt` и `requirements-dev.txt`:

```powershell
python scripts/checkpoint.py --participant Dinmukhammed --branch dev-dinmukhammed --summary "Проверены изменения backend"
python scripts/checkpoint.py --participant Dinmukhammed --branch dev-dinmukhammed --summary "Проверены изменения backend" --publish
```

Для Ilyas: `--participant Ilyas --branch dev-zoro`; `dev-ilyas` использовать после его собственного подтверждённого перехода. Не запускать за другого участника. `--summary` обязателен, одна содержательная строка до 200 символов, без секретов. Блокирующая проверка возвращает код 1 и конкретную безопасную причину; успешная — код 0.

## Что проверяется

1. Точный репозиторий Git, текущая личная ветка и единственный fetch/push URL origin: `BAITC-Hacks/hack-95a1b8c8-that-s-la-peace` на GitHub по HTTPS или SSH. URL с учётными данными или другого репозитория не разрешён.
2. Отсутствие незавершённых merge/rebase/cherry-pick/revert/bisect и конфликтов. Remote читается и выполняется `fetch` только своей ветки. Remote впереди, расхождение, отсутствующая удалённая ветка и уже существующие неопубликованные локальные коммиты блокируют **оба режима**. Для простоты gate требует исходное `HEAD == origin/<личная ветка>`; первоначальную публикацию и проверку прежних локальных коммитов интегратор выполняет отдельно.
3. Владение всеми изменёнными, staged и неигнорируемыми untracked файлами; у переименования проверяются старое и новое имя. Dinmukhammed: backend, data, scripts, tests/backend, tests/integration, общие docs и перечисленные корневые файлы запуска. Ilyas: frontend, tests/ui, docs/DEMO.md, docs/EXPERT_CHECK.md, docs/handoffs/ilyas.md. Чужие изменения блокируют checkpoint целиком.
4. Опасные пути `.env*`, `.git`, приватные ключи и имена файлов с credentials/secrets блокируются. Локальная эвристика проверяет целиком изменённые текстовые файлы и staged blobs, известные форматы токенов, ключи, пароли и URL с credentials. Значения не выводятся. Только явные фиктивные литералы с `FAKE_`, `DUMMY_` или `PLACEHOLDER` разрешены; такой маркер не освобождает остальной файл от проверки. Бинарные файлы, не-UTF-8, файлы больше 5 МБ, symlink и submodule требуют отдельного ручного review. Эвристика не доказывает отсутствие любых секретов; возможны ложные срабатывания, автоматического обхода нет.
5. Полный `python -m pytest tests/backend -q`, затем новый временный сервер из этой копии на собственном зарезервированном свободном loopback-порту и `scripts/smoke.py`. Сервер не подменяется уже работающим приложением; останавливается только созданный процесс и его дочерний сервер, включая случай ошибки smoke. На Windows используется `taskkill /PID <собственный PID> /T /F` без shell; чужие процессы по имени или порту не останавливаются. Браузерную и человеческую приёмку этот gate не заменяет.
6. После тестов повторно проверяются HEAD, ветка, индекс, status, содержимое изменённых файлов и remote. Любое изменение блокирует публикацию. В `--publish` staging делается только по конкретному разрешённому списку; пустой commit запрещён. Содержимое commit сравнивается с проверенным staged diff, затем проверяются remote и результат push по точному SHA.

## Побочные действия и доказательства

Даже `check-only` выполняет fetch (обновляет remote refs), тесты, временный сервер и пишет локальный JSON в Git-служебную папку `checkpoint-evidence` (`git rev-parse --git-path checkpoint-evidence`). Он не stage/commit/push файлы. В JSON сохраняются время UTC, режим, SHA, список путей, хеш snapshot и фактически выполненные проверки; исходные файлы, значения секретов и сырые логи команд не сохраняются. Общие PROGRESS/COMPLIANCE автоматически не меняются.

При поздней ошибке `--publish` уже подготовленный индекс или локальный commit остаётся для осознанного разбора: gate ничего не откатывает. Если push прошёл, но его проверка не завершилась, сначала сверить remote; повторный запуск не означает повторное разрешение на непроверенную публикацию. После удачного личного push точный SHA передаётся единственному интегратору для отдельной сборки и приёмки общей версии.

## Проверка самого gate

```powershell
python -m pytest tests/backend/test_checkpoint.py -q
```

Тесты используют только временные локальные bare-репозитории и подменённый список допустимых origin внутри теста. В рабочем CLI нет параметра или переменной окружения для обхода точного GitHub origin. Реальные GitHub-ветки тестами не изменяются.
