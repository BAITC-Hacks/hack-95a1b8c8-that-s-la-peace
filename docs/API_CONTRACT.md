# API v1 для параллельной работы

Этот контракт реализован серверной частью в backend/ и frontend Ilyas. Совместный прогон общей сборки описан в [отчёте 23.09.2026](integration/20260923-1435.md); независимый технический запуск этой версии агентом Ilyas подтверждён в EXPERT_CHECK пакетом e8bf9c2. Человеческая оценка остаётся отдельной. Владелец — Dinmukhammed. Обе части используют эти имена полей. Несовместимые изменения не делаются без синхронизации второго участника.

## Общие правила

JSON UTF-8, один сервер http://127.0.0.1:8000, frontend вызывает относительные /api/.... Все поля, перечисленные в ответах ниже, присутствуют; неизвестные дополнительные поля frontend может игнорировать. Даты — YYYY-MM-DD. API-version — целое число 1. dataset_version — SHA-256 фактического набора данных, одинаковый в meta и recommendations. HTTP errors не подменять обычной пустой выдачей.

## GET /api/health

Готовый сервер: HTTP 200, `{"status":"ok","api_version":1,"dataset_count":66}`. Ошибка загрузки данных: HTTP 503 в общей схеме ошибки. Health подтверждает готовность API; наличие frontend проверяется отдельным запросом `/` и браузерным сценарием.

## GET /api/meta

HTTP 200 с обязательными полями:

- api_version: 1.
- dataset_version: string SHA-256.
- dataset_count: integer.
- cities, categories, event_types, languages: массивы уникальных строк из полного каталога с фиксированной сортировкой Unicode; frontend сохраняет их значения без перевода отправляемых enum.
- date_range: {"min":"2026-09-23","max":"2026-12-31"}. Это объявленное покрытие, не вычисленный интервал min/max занятых дат.

Категории общие, не ограничены городом; поэтому пользователь может получить содержательный no_category_in_city.

## POST /api/recommendations

Пример запроса:

```json
{
  "city": "Алматы",
  "event_date": "2026-10-15",
  "event_type": "корпоратив",
  "category": "Ведущий",
  "budget_kzt": 1000000,
  "duration_hours": null,
  "language": null
}
```

Обязательные поля: city, event_date, event_type, category, budget_kzt. Бюджет — JSON integer >0, не boolean или строка. duration_hours — конечное положительное число либо null; language — известная строка либо null. Пропуск optional эквивалентен null. Не вводим произвольный верхний предел бюджета и не создаём автоматический отказ на основании сегодняшней даты: используем объявленное окно данных.

Текущий браузерный клиент вводит бюджет как точный JavaScript integer: от 1 до 9 007 199 254 740 991 включительно (`Number.isSafeInteger`). Это техническая граница UI, не ограничение backend API и не максимальная стоимость мероприятия. Все цены исходного каталога находятся внутри неё. Клиентам, использующим большие целые API, нужно сохранять их точность при формировании JSON; браузерный UI такие суммы не поддерживает. Существующее поведение v1 сохраняется явно, без нового серверного потолка.

Краевые пробелы строк удаляются, enum сравниваются с опубликованными справочниками. Дата реальная, внутри окна включительно. Неизвестное значение справочника, неверный тип, пустая обязательная строка и неожиданные поля дают 422. Корректная глобально категория без профилей в городе даёт обычный 200 no_category_in_city.

## Ответ подбора

HTTP 200 для всех трёх исходов. Обязательные поля:

| Поле | Значение |
| --- | --- |
| api_version | 1 |
| dataset_version | SHA-256 используемого набора |
| status | matched / no_category_in_city / no_matches |
| message | Короткое фактическое пояснение результата, для <3 карточек причина нехватки |
| cards | Массив 0–3 карточек в окончательном порядке |
| total_in_city_category | Число профилей нужного города и категории до остальных фильтров |
| eligible_count | Число прошедших все фильтры до ограничения top-3 |
| exclusions | Объект с integer >=0 для busy, budget, event_type, language, duration |
| suggestions | Массив 0–2 проверенных альтернативных запросов |
| explanation_mode | deterministic / llm / deterministic_fallback — честный способ формирования текстов данного ответа |

matched: eligible_count>0, cards содержит min(3,eligible_count). no_category_in_city: total_in_city_category=0, eligible_count=0, cards=[], exclusions все нули. no_matches: total_in_city_category>0, eligible_count=0, cards=[]. Для обоих пустых исходов message непустой.

Exclusions вычисляются внутри исходной группы города/категории независимо по каждому ограничению. Один человек может нарушать несколько условий; числа могут пересекаться. Не суммировать их как число отдельных исключённых профилей. При незаданном языке/длительности соответствующий счётчик равен 0.

Карточка имеет обязательные поля:

| Поле | Тип и смысл |
| --- | --- |
| id | Уникальный строковый id исходного профиля |
| name | anon_name |
| category | Запрошенная категория, принадлежащая categories профиля |
| city | Строка из исходных данных |
| price_from_kzt | Integer, начальная цена услуги |
| explanation | 1–2 конкретных предложения, основанных на профиле и запросе |
| languages | Массив строк из профиля |
| max_hours | Положительное число либо null — неприменимо |
| description_excerpt | Содержательный дословный фрагмент description, без выдуманных фактов |
| synthetic | Boolean |
| city_imputed | Boolean |
| price_imputed | Boolean |
| source | provided / team_added; исходные 13 synthetic также имеют source=provided |

Frontend не пересортировывает карточки и не сочиняет объяснения. Цена отображается «от … ₸». Факт соответствия начальной цены бюджету не обещает итоговую стоимость всего заказа. Если используется fallback после ошибки LLM, explanation_mode=deterministic_fallback, а UI не заявляет успешный ответ внешней модели.

## Suggestions как отдельные действия пользователя

Реализованы два вида: change_date и increase_budget. Для matched suggestions=[]; для пустой выдачи можно вернуть до одного предложения каждого вида, порядок: change_date затем increase_budget. Для отсутствующей категории изменение даты/бюджета не помогает — suggestions=[].

Каждый элемент содержит kind, message, request (полный валидный запрос в схеме выше) и eligible_count (integer >0). Меняется ровно одно поле исходного нормализованного запроса. Сервер проверяет совет теми же фильтрами без повторного рекурсивного поиска советов.

- change_date: ближайшая другая дата в объявленном календаре, для которой есть подходящие; при одинаковом расстоянии более ранняя. Все остальные параметры неизменны.
- increase_budget: минимальный price_from_kzt кандидата, который удовлетворяет всем остальным ограничениям; новый бюджет строго больше старого. Формулировка относится к начальной цене, не гарантированной сумме заказа.
- Если изменением одного условия нельзя получить результат, ничего не предлагать.

UI показывает предложение отдельно и применяет только по нажатию, затем отправляет новый запрос. Автоматически менять введённые пользователем условия нельзя.

## Ошибки

HTTP 422 для неверного запроса:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "Проверьте параметры мероприятия.",
    "fields": {"event_date": "Дата должна быть внутри календаря 23.09.2026–31.12.2026."}
  }
}
```

HTTP 503 для недоступного сервиса: такой же error-объект с code=service_unavailable, понятным message и fields={}. Не возвращать стек/секреты. Backend приводит встроенные ошибки валидации к этому формату, frontend не должен одновременно гадать о двух разных схемах. Неожиданная сетевая/HTTP ошибка показывается отдельно от no_matches.

## Приёмка совместимости

Контрактные проверки Dinmukhammed подтверждают поля, типы, статусы и инварианты. Ilyas проверяет отправляемый JSON и отображение реальных ответов. Фикстуры разработки явно обозначены; финальный index.html не использует их автоматически. Все будущие фактические изменения схемы отражаются здесь до передачи другой стороне.

Техническая опора выбранного способа раздачи файлов: https://fastapi.tiangolo.com/tutorial/static-files/ . Пакетные версии зафиксированы в requirements.txt и requirements-dev.txt; наличие этой ссылки не является проверкой запуска нашего проекта.

## Ограничение HTTP-запроса и заголовки

Основной Python-сервер допускает тело запроса до 16 384 байт включительно. Ограничение проверяется до разбора JSON по фактически принятым байтам, в том числе при отсутствии или неверном Content-Length. Заведомо превышающий лимит Content-Length отклоняется сразу. Это граница размера транспорта, а не новая семантика фильтров или бюджета.

Превышение возвращает HTTP 413 в общей форме ошибки: `{"error":{"code":"request_too_large","message":"Размер тела запроса превышает 16 КиБ.","fields":{}}}`. Обычные запросы, API v1 и успешные ответы сохраняются. Все HTTP-ответы получают `X-Content-Type-Options: nosniff` и `Referrer-Policy: no-referrer`. CSP ограничивает ресурсы публичного frontend текущим origin; служебные `/docs`, `/redoc` и `/openapi.json` не получают эту CSP, чтобы сохранить загрузку Swagger/ReDoc.
