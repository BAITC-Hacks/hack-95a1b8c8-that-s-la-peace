## Что показать

Заказчик выбирает подрядчика из каталога своего города. Он вводит город, дату, формат, категорию и бюджет; получает до трёх свободных подходящих профилей с объяснениями по фактам. Бронирования и уведомления не входят в задачу. Приоритет ТЗ — объяснения и честные ограничения.

1. Кратко назвать проблему и пользователя, показать фактически работающий путь ввода и результата.
2. Выполнить плотную категорию, редкую категорию и пустую выдачу из таблицы ниже.
3. Повторить тот же запрос, затем изменить только дату. Отдельно показать календарь площадки.
4. Объяснить реальный pipeline: источник данных, жёсткие ограничения, ранжирование, формирование объяснения, место AI. Не заявлять ещё не реализованный подход.
5. Назвать измеренное время, ограничения и фактический вклад каждого участника. Будущие функции обозначить планами. Обязательная длительность выступления в прочитанных материалах не задана.

Для D1 → D2 меняется множество допустимых профилей, но изменение именно видимого top-3 необходимо проверить после реализации ранжирования.

## Что проверить на карточках и в ответах

- Имя, запрошенная категория, город, цена **«от … ₸»** и 1–2 содержательных предложения. Цена не означает подтверждённую стоимость заказа.
- Убрать имена мысленно или во временной копии ответа: объяснения карточек одного запроса должны оставаться различимыми. Проверить конкретный факт описания и соответствие условиям; одинаковая общая похвала не проходит.
- Ни одного занятого кандидата, в том числе среди площадок. Повтор D1 и V1 на той же версии данных должен сохранить последовательность `id`; буквальное совпадение AI-текста ТЗ не требует.
- Показать `synthetic`, `city_imputed`, `price_imputed` понятными словами. В V1 у `HK-64395` город и цена проставлены при подготовке данных; у `HK-90011` синтетический профиль исходного набора и проставленная цена. Эти профили не созданы командой. Собственные добавления, если появятся, раскрыть отдельно.
- Пустой `max_hours` у флористов, декораторов и сувениров означает «присутствие неприменимо», а не ноль часов. Не обещать длительность, которой нет в данных.
- `exclusions` — независимые счётчики причин, их нельзя складывать как число исключённых профилей. Для D1: заняты 2, выше бюджета 2, неподходящий формат 1, всего допустимых 6 из 10.
- Замерить время от отправки до содержательного ответа для каждого показанного запроса; ориентир ТЗ — до 10 секунд. Отдельно записать первый запуск и повтор, если кэш влияет на результат.

## Ошибки и честные ограничения

| Проверка | Ожидаемое поведение по предлагаемому контракту | Статус |
| --- | --- | --- |
| Пустое обязательное поле, бюджет 0 или отрицательный, длительность 0 | Понятная ошибка поля; API v1: HTTP 422, `invalid_request`; исправление сохраняет остальные введённые значения | NOT VERIFIED |
| Нереальная дата `2026-11-31`, даты `2026-09-22` и `2027-01-01` | Ввод отклонён. Известное окно календаря — 23.09–31.12.2026; вне него нельзя обещать свободу | NOT VERIFIED |
| Язык или длительность исключают кандидатов | Объяснённая нехватка/пустой результат, а не техническая ошибка | NOT VERIFIED |
| Недоступен API или обязательный AI-сервис | Понятная ошибка и возможность повторить; API v1 для отказа сервиса: HTTP 503, `service_unavailable`; нет фиктивных успешных карточек | NOT VERIFIED |
| Повтор после восстановления сервиса | Успешный полный сценарий, без показа старой выдачи как результата нового запроса | NOT VERIFIED |

Проверки отказа выполнять только в своей изолированной среде. Fixtures могут проверять UI при явной маркировке, но не доказывают реальную фильтрацию, работу AI или готовность к сдаче.
