## Цель и текущее состояние

Сервис принимает параметры мероприятия и из выданного каталога предлагает до трёх подрядчиков с конкретными объяснениями. В стартовом пакете есть план, контракт и предоставленный CSV. Наличие этих документов не означает, что приложение уже реализовано, запущено или протестировано.

Репозиторий: https://github.com/BAITC-Hacks/hack-95a1b8c8-that-s-la-peace.git

- Dinmukhammed работает в `dev-dimalarp`.
- Друг создаёт свою ветку. Используй её фактическое имя, не выдумывай `dev-ilyas` и не переключайся на ветку Dinmukhammed.
- Общая проверяемая версия — `integration`. Одноразовый bootstrap: координатор создаёт её от SHA подготовленного пакета dev-dimalarp с документами и данными; статус приложения NOT RUN. Проверка работающей сборки обязательна для последующих интеграций кода.
- Единственный интегратор — Dinmukhammed и его Codex. Друг пушит только свою ветку.
- `main` не меняем до отдельного прямого указания пользователя о финальном объединении. Текущая просьба уже разрешает обычные commits/push личных веток и проверенное объединение в integration; повторное подтверждение каждого такого действия не нужно.
- Новое распределение заменяет ранний предложенный TASK_SPLIT и его требование отдельно разрешать каждое объединение. Фактическое ТЗ и новые прямые указания пользователя сохраняют приоритет.

## Общая архитектура

Python 3.12 + FastAPI + Uvicorn. Frontend — обычные HTML/CSS/JavaScript без сборки и CDN. Один процесс обслуживает API и frontend по http://127.0.0.1:8000. UI вызывает относительные `/api/...`; ключи или отдельные адреса API в браузере не нужны. Для 66 профилей достаточно чтения CSV в память. БД, регистрацию, бронирование, уведомления и дообучение не добавлять.

Dinmukhammed создаёт и проверяет `python run.py`: команда запуска из корня после установки зафиксированных зависимостей. Параметр `--port` позволяет отдельно проверить candidate, например `python run.py --port 8002`; по умолчанию порт 8000. Ожидаемый путь установки: `python -m venv .venv`, запуск pip через Python этого окружения, затем `python run.py` из активированного окружения. Это целевой контракт запуска, сейчас не подтверждённая возможность. Точные реально выполненные команды для Windows и проверенной второй ОС фиксируются в README; непроверенную ОС не объявлять поддерживаемой.

Предлагаемый entry point — `backend.app:app`. API-маршруты регистрируются до раздачи frontend. Сервер раздаёт только каталог frontend, не корень репозитория или data. Если UI ещё не получен, API может работать самостоятельно, но полный интерфейс не объявлять готовым.

## Обязательный объём

- Вход: город, дата, формат мероприятия, категория, бюджет в тенге; язык и часы необязательны.
- Фильтры: город/категория, занятость, цена «от» в пределах бюджета, формат, запрошенные язык и длительность.
- Пустой max_hours означает неприменимое время присутствия, не ноль и не обещание неограниченной работы.
- Выход: 0–3 карточки с именем, категорией, городом, ценой «от» и 1–2 конкретными предложениями. Использовать проверяемые отличительные факты профиля.
- Занятых подрядчиков не показывать среди результатов исходного запроса. Площадки обрабатываются точно так же.
- Одинаковые параметры и версия данных дают одинаковые id в том же порядке. Явный последний ключ сортировки — id.
- Различимы matched, no_category_in_city и no_matches. Если карточек меньше трёх, показать причину словами.
- Смена даты может изменить выдачу из-за занятости; показать это в живом демо, включая изменение видимого top-3.
- Ориентир ответа — до 10 секунд. Проверять по факту, не обещать без замера.
- Приоритет ТЗ: объяснения > честные пустые/редкие/занятые категории > скорость > интерфейс.

Оценка: работоспособность 25, техническая реализация 25, README и воспроизводимость 25, ценность 15, потенциал и оригинальность 10. Баллы не являются гарантией оценки.

## Наши две идеи

1. Сравнение по фактам: рядом с объяснением видны языки, максимальное время присутствия и отличительный фрагмент описания. Цена «от» не превращается в гарантированную стоимость. Нельзя выдумывать отзывы, качество, опыт или рейтинг.
2. Помощь при пустой выдаче: сервер ищет альтернативу, меняющую только дату либо только бюджет, проверяет её теми же фильтрами и возвращает suggestion. UI применяет предложение только после нажатия пользователя. Нет проверенной альтернативы — нет совета. Сначала обязательный сценарий, затем эти улучшения.

Необязательный LLM может помогать формулировке объяснений, но не нарушать фильтры или определять порядок. Основной проверяемый сценарий должен быть доступен без личного платного аккаунта участника. Детерминированную обработку не называй LLM. Если реальный AI-сервис подключён, документируй модель, передачу данных, тайм-аут, кеш и честный резервный режим. Использование AI-агента при разработке фиксируется отдельно от AI внутри продукта.

## Ритм каждого часа

Рабочее расписание из предоставленных материалов: 23.09.2026, 13:00–18:00 UTC+05:00; уточнённые официальные объявления имеют приоритет.

- До :40: завершить небольшой согласованный результат. Не начинать крупную новую функцию перед checkpoint.
- :40–:43: проверить свою часть, просмотреть diff и состав staged файлов, обновить свой handoff.
- До :45: содержательный commit и обычный push в свою ветку; проверить remote SHA и передать точные branch + SHA интегратору.
- :45–:50: интегратор объединяет зафиксированные SHA, проверяет совместный запуск и пользовательский сценарий, затем обновляет integration обычным push.
- После :50: сверить remote SHA и записать, что реально работает. Если интеграция не прошла, не объявлять её успешной; общая ветка сохраняет последнюю проверенную версию.

Контрольные окна: 13:45–13:50, 14:45–14:50, 15:45–15:50, 16:45–16:50, 17:45–17:50. На первом окне цель — форма → настоящий API → карточки и объяснённый пустой результат. Если времени не хватает, честно фиксировать выполненную часть и блокер. Пустые коммиты, выдуманное время и «зелёный» отчёт вместо запуска запрещены.

План пяти часов: 13–14 — основной сквозной сценарий; 14–15 — все ограничения и объяснения; 15–16 — сравнение и советы; 16–17 — чистая установка и проверка другом; 17–18 — исправления и сдача. С 17:30 не расширять функции. К 17:50 подготовить проверенную финальную версию; main и платформа требуют отдельного решения пользователя до фактического дедлайна.

Этот файл сам не запускается по расписанию. Пока агент работает, он сверяет текущее время; капитан ставит будильники. Фоновое выполнение или автоматические почасовые commits не обещать без отдельно настроенного и проверенного механизма. Новые часы не считать подтверждёнными заранее.

## Передача личного результата

Перед каждым commit проверить `git status --short --branch`, remote и diff; запускать релевантные проверки. Добавлять только свои конкретные файлы, не `git add .`. Чужие изменения не удалять и не откатывать. Если нужная ветка уже есть, использовать её; не создавать дубль.

Свой handoff содержит: участник/фактическая ветка, время с UTC+05:00, изменённые файлы, реализованные требования, точные команды проверки и результаты, ограничения, ближайшая задача. SHA содержащего handoff коммита получают после commit и передают в ответе; не пытаться вписать в файл его собственный hash.

После проверки текущей ветки выполнить `git push --set-upstream origin HEAD:refs/heads/<своя-ветка>` при первой публикации или `git push origin HEAD:refs/heads/<своя-ветка>` в следующих циклах. Подставлять фактическое имя своей ветки; не полагаться на push.default. Проверить `git ls-remote --heads origin <своя-ветка>`. Если remote сдвинулся другим писателем, остановиться и выяснить состояние; без force, rebase или reset --hard.

Отчёт участника: время, ветка, результат, тесты, SHA, remote подтверждён/не подтверждён, блокеры, что можно интегрировать. Интегратор дополнительно даёт URL запуска и результат сквозного сценария.

## Протокол единственного интегратора

1. Получить фактическое имя ветки друга и готовые SHA обеих частей. `git fetch origin`; записать точные SHA. Новые коммиты после фиксации входят в следующий цикл.
2. Проверить, что заявленные SHA относятся к соответствующим remote-веткам. Старые SHA допустимы как осознанно выбранная стабильная версия; явно записать это.
3. Создать отдельный временный worktree с новой локальной веткой `integrate-YYYYMMDD-HHMM` от origin/integration. Путь и имя должны быть свободны. Личную рабочую ветку и незакоммиченные изменения не перемещать.
4. В этом worktree обычными merge включить точный SHA Dinmukhammed, затем точный SHA друга. Без squash/rebase/force. Конфликт требует просмотра и осмысленного решения с владельцем; не выбирать целиком ours/theirs вслепую.
5. Установить зависимости из lock/requirements в чистое окружение, запустить тесты, сервер и браузерный сценарий по README. Проверить `/`, `/api/health`, `/api/meta`, один реальный подбор и два пустых состояния. Mock-страница не проходит интеграцию. Запускать именно процесс из candidate-worktree, проверить успешное занятие выбранного порта; нельзя случайно тестировать сервер личной ветки. Если 8000 занят, выбрать отдельный свободный порт через --port и записать его в отчёт. Чужой процесс автоматически не завершать.
6. Записать фактические base/backend/frontend SHA, команды, результаты и ограничения в `docs/integration/YYYYMMDD-HHMM.md`; commit только этого отчёта, если он добавлен. Если после проверок менялся код, повторить затронутые проверки.
7. Перед push снова fetch. Если origin/integration изменился после выбранной базы, не публиковать старый candidate: создать новую candidate-копию от новой базы, включить выбранные SHA, повторить весь обязательный сквозной минимум и записать актуальный отчёт. Не затирать новую общую версию.
8. После успешной проверки обычный `git push origin HEAD:refs/heads/integration` из candidate worktree. Проверить remote SHA и что оба выбранных SHA являются его предками. При отказе push не форсировать.
9. После публикации оба участника на чистых личных рабочих деревьях делают fetch и обычный merge origin/integration в свои ветки. Иначе следующий цикл снова принесёт старые версии общих файлов. Коммит участника не нужно создавать, если изменений нет.

Если проверка сломалась, не пушить candidate в integration. Исправить свою часть в своей ветке, передать новый SHA и повторить интеграцию. Незавершённый merge можно abort только в собственной чистой до merge candidate-копии, без удаления пользовательской работы. Worktree сохранять до завершения проверки, не удалять автоматически чужие/грязные каталоги.

Первый handoff frontend может иметь `backend integration: NOT RUN`, если друг проверил его на помеченных фикстурах, а backend ещё не получен. Такой handoff разрешает пробное объединение в candidate, но не публикацию непроверенного приложения: интегратор проверяет реальный API вместе с UI, затем друг повторяет проверку полученной integration. Не создавайте взаимное ожидание перед первым merge.

## Условия готовности общей версии

Чистая установка по README, открывающийся UI, весь основной сценарий на настоящих данных, согласованный контракт, стабильный порядок, обе причины пустой выдачи, редкая категория, отличие двух дат, объяснения на фактах, секреты отсутствуют, версии в отчёте совпадают с remote. Отдельно проверить язык/длительность, пределы дат, ошибочный ввод и недоступный сервис. Статусы НЕ ПРОВЕРЕНО не превращать в ПРОЙДЕНО.

Интеграция — локально запускаемая общая версия. Интернет-деплой ещё не создан и этим файлом не обещан. Финальная подача «Сдать решение» на платформе — отдельное действие капитана; push не заменяет его.
