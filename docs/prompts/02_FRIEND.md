## Ветка и получение общего пакета

Сначала проверь git status, remote и текущую ветку. Я создаю свою ветку сам; используй фактическое имя. Если текущая ветка main, integration или dev-dimalarp, не начинай там мои изменения: узнай имя моей отдельной ветки. Не выдумывай его. Если её ещё нет и я дал конкретное имя, создай её от актуальной origin/integration. Если уже существует, сохрани изменения, fetch и обычным merge получи общий пакет из origin/integration на чистом дереве. Не делай reset --hard/rebase/force.

Если на этой машине ещё нет копии, клонируй именно этот репозиторий, затем выбери мою ветку. Не создавай новый репозиторий. До редактирования прочитай docs/prompts/00_SHARED_PLAN.md, docs/API_CONTRACT.md, docs/CASE_REQUIREMENTS.md, data/README.md, README и текущее дерево. ## Архитектура интерфейса

Обычные HTML/CSS/JavaScript в frontend, без обязательной сборки, CDN, стороннего аккаунта и отдельной БД. Стартовые файлы: index.html, styles.css, app.js, при необходимости локальные assets. Общий Python/FastAPI сервер раздаёт frontend и API на одном http://127.0.0.1:8000. Используй относительные `/api/meta` и `/api/recommendations`; адрес машины автора не зашивать. Базовый запуск создаёт Dinmukhammed.

До появления backend можно делать помеченную тестовую страницу `frontend/dev.html` с фикстурами внутри `frontend/dev/`; обычный index.html не должен молча переключаться на заглушки при ошибке сети. После создания dev.html локальный preview: `python -m http.server 8001 --directory frontend`, адрес `http://127.0.0.1:8001/dev.html`. Он обслуживает только frontend и не заменяет Python API. Фикстуры — не доказательство готового приложения. После получения API обязательно проверить настоящие запросы. Отсутствие backend не останавливает создание формы и состояний UI.

## Что реализовать

1. Понятный интерфейс на русском: выбор города, даты, формата, категории, бюджета в тенге; язык и часы необязательны. Справочники и диапазон дат загрузить из GET /api/meta. Не фильтровать категории по городу так, чтобы исчезала возможность показать no_category_in_city.
2. POST /api/recommendations отправляет ровно поля city, event_date, event_type, category, budget_kzt, duration_hours, language. Дата YYYY-MM-DD, бюджет integer >0, часы положительное число или null, язык строка или null. Пустые необязательные inputs превращаются в null, не 0 и не пустую строку.
3. Показать от 0 до 3 карточек в порядке API. Имя, категория, город, цена с подписью «от», объяснение целиком. Не придумывать объяснение на клиенте и не пересортировывать карточки.
4. Отдельно отрисовать три обычных исхода: matched, no_category_in_city, no_matches. Показать message, число подходящих и объяснение нехватки. Если найдено 1 или 2, не дополнять фиктивными карточками. Пустая выдача — не красная ошибка соединения.
5. Показать фактические отличия: languages, max_hours с «присутствие по часам неприменимо» для null, description_excerpt. Отметить synthetic, city_imputed и price_imputed понятными подсказками. Не называть 53 исходных nonsynthetic профиля подтверждённо действующими компаниями.
6. Suggestions показывать отдельным блоком «Можно изменить условия», с явным указанием меняемой даты или бюджета. По нажатию применить весь серверный suggestion.request к форме и выполнить новый запрос. До нажатия запрос и результаты не меняются. Пустой suggestions скрывает блок, не создаёт выдуманные советы.
7. Loading, валидация полей, сетевые ошибки и 503 отличимы. При ошибке старый результат не выдаётся за ответ на новую форму. Для повторных запросов AbortController или счётчик запроса защищает от запоздалого ответа.
8. Все поля имеют label, доступна клавиатура, loading/result объявляются через aria-live, ошибки привязаны к полям. Строки API/CSV выводятся через textContent, не небезопасный innerHTML. Проверить мобильную ширину и отсутствие обрезанных объяснений.
9. Сделать аккуратный интерфейс без лишних разделов. В ТЗ важнее объяснения и работающие состояния, чем декоративная анимация. Бронирование, оплата и сообщения подрядчику вне задачи.

Полная обязательная схема, example payloads, ошибки и правила suggestions находятся в docs/API_CONTRACT.md. Не создавать альтернативные названия полей. Если нужна правка схемы, согласовать её до изменения.

## Проверки UI и демонстрация

Проверить реальные действия браузером: отправка формы, карточки 1/2/3, обе причины пустой выдачи, ошибка ввода, loading, недоступный backend, быстрые повторные запросы, применение совета. Фикстуры разрешены для разработки компонентов, но финальная проверка только на настоящем API.

В docs/DEMO.md записать точные запросы, действия и ожидаемые наблюдаемые свойства. Обязательны плотная категория осенью, редкая, отсутствие результата, повторный запрос с тем же порядком и две даты с различным видимым top-3 из-за занятости. Готовые исходные ориентиры: Алматы/Ведущий/корпоратив/1 000 000 ₸ на 15 октября 2026 — 6 подходящих до top-3, на 16 октября — 4; Алматы/Флорист/свадьба на 15 октября при том же бюджете — 2; Астана/Флорист — единственный занят. Зарубежье/Ведущий — категория отсутствует. Пара дат должна быть проверена после окончательного ранжирования: изменение общего числа не гарантирует изменение видимых трёх карточек.

В docs/EXPERT_CHECK.md после получения общей версии записать чистый запуск на моей машине строго по README: SHA, ОС, версии, команды, реальный результат, обнаруженные пропуски. Если нужна устная подсказка или скрытый файл, это дефект инструкции. Не исправляй общий README сам, передай конкретную правку владельцу. До запуска статус NOT RUN, не PASS.

Первый handoff разрешено передать с `backend integration: NOT RUN`, если UI проверен на явно помеченных фикстурах, а backend ещё не опубликован. Указать «готов к проверке в candidate», не «приложение работает». Dinmukhammed первым соединит этот SHA с backend и проверит живой сценарий, после чего ты повторишь проверку полученной integration. Не жди интеграцию как условие отправки первого UI.

## Мой checkpoint

До :40 закончить небольшой реальный результат; :40–:43 проверки и просмотр своих файлов; до :45 commit и push моей ветки. Добавлять только мои файлы, без git add .; проверить секреты и diff. Не менять Git author/email ради отчёта. В docs/handoffs/ilyas.md указать реальную ветку, результат, файлы, команды проверки, фактические PASS/FAIL/NOT RUN и ограничения.

После проверки текущей ветки и commit получить SHA, выполнить `git push origin HEAD:refs/heads/<фактическая-своя-ветка>` (при первой публикации с --set-upstream), проверить git ls-remote. Не использовать неявный push, который может зависеть от настройки push.default. В ответе выдать готовый текст для Dinmukhammed: «Ветка: …; SHA: …; контракт v1; готово: …; проверки: …; ограничения: …; можно интегрировать: да/нет». Не пытайся вписать в commit его собственный hash. Чужую часть не считать проверенной.

Dinmukhammed включает твой SHA в candidate и проверяет общую сборку к :50. После подтверждения integration на чистом рабочем дереве fetch и обычным merge подтяни её в свою ветку. При конфликте не выбирать весь ours/theirs; уточнить владельца и сохранить обе нужные части. Main и integration сам не пушить.

## Первые действия прямо сейчас

Определить свою ветку и получить общий пакет. Создать форму и все состояния на согласованной схеме, затем связать с API. Не ждать готовой AI-интеграции ради начала UI. Не обещать фоновое соблюдение расписания одним текстом промпта; сверяй время во время работы и напоминай мне о checkpoint. Продолжай до работающей своей части и проверенного handoff.
