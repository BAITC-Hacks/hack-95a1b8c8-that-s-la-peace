## Порядок чистой проверки

1. Подтвердить официальный remote, сдаваемую ветку и разрешение на интеграцию. Получить уже отправленную **объединённую** версию в новую чистую директорию/изолированную среду. Записать полученный SHA и сверить его с remote. Существующую рабочую папку команды не очищать.
2. Следовать README буквально. До начала владелец общего запуска должен добавить проверенные команды установки, подготовки данных/модели, окружения, запуска, остановки и повторного старта. В этом документе команды не угадываются; сейчас этот шаг заблокирован отсутствием инструкции.
3. Не переносить `.env`, личные cookies/авторизацию, незакоммиченные обязательные файлы, `node_modules`, локальные окружения и кэши как скрытую зависимость. Использовать только доступные эксперту разрешённые материалы и доступы. Не передавать личные API-ключи.
4. Пройти D1–D6 и V1–V2 из [DEMO.md](DEMO.md) через реальный интерфейс и API. Записать вход, фактические `id` в порядке ответа, количества, текст пояснения и задержку. Проверить обязательный основной путь целиком; открытая страница/HTTP 200 недостаточны.
5. Повторить D1 и V1 без изменения параметров и версии данных; порядок `id` совпадает. Проверить конкретность объяснений без имён, календарь площадки, редкую категорию и два разных пустых исхода. Проверить optional-поля, некорректный ввод, отказ сервиса и восстановление по DEMO.
6. Проверить применимые серверные секреты, отсутствие их во frontend и безопасных логах, фактическую AI-функцию, данные/модель, версии зависимостей. Симуляции подписаны и не засчитываются как реальная основная функция. Доступ эксперта и срок его действия проверить фактически; если зависит от внешнего сервиса, согласовать с организатором период проверки и очистки временных ключей/данных.
7. Остановить и снова запустить по README, повторить основной сценарий. Если другой участник проверяет инструкцию, он использует своё устройство/разрешённую среду без устных подсказок. Записать каждую понадобившуюся недокументированную настройку как проблему.
8. Исправить обнаруженное до дедлайна; после изменения кода, данных, модели, зависимостей или конфигурации повторить затронутые проверки на новом отправленном SHA. Документальные изменения после проверенного SHA перечислить отдельно. Финальный SHA фиксируется после последнего коммита, без попытки вписать хеш внутрь него самого.

Разрешённые статусы: PASS / FAIL / NOT VERIFIED / BLOCKER / N/A с причиной. PASS означает фактически выполненную проверку и приложенное доказательство. NOT VERIFIED не означает ожидаемый успех.

## Передача и решение о готовности

Проверка `dev-zoro` полезна для части Ilyas. Проверка UI на fixtures полезна для его состояний. Ни одна из них не заменяет чистую приёмку объединённой версии с реальным API и требуемой функциональностью.

Ответственный за интеграцию получает коммиты Ilyas, изменённые файлы, зависимости/миграции, выполненные проверки, конфликты и оставшиеся блокеры. После интеграции сюда вносится фактический результат общего запуска. Без него общая техническая готовность не подтверждается.

- Часть Ilyas: готова к проверке в candidate; API 9/9, HTTP 2/2 и браузерные
  проверки frontend на явно синтетических ответах — PASS. Реальный backend — NOT VERIFIED.
- Готовность общей версии: NOT VERIFIED — интеграция и независимый запуск не выполнены.
- Подача через платформу: **не подтверждена**. Финальный push или PR не заменяют «Сдать решение»; фактическое подтверждение предоставляет капитан. Этот документ не разрешает отправку формы.
