# Архитектура подбора

Сервер работает локально на Python 3.12/FastAPI. При запуске CSV загружается в память, проверяется и получает SHA-256. Ошибка файла переводит API в 503, а не в успешный пустой каталог. Перезапуск требуется только при изменении данных или кода.

## Поток запроса

Строгая схема проверяет поля, типы, положительные числа и диапазон дат. Справочники проверяются по каталогу. Затем выбирается группа города и категории. Если её нет — no_category_in_city. Внутри группы независимо проверяются дата, начальная цена, формат, запрошенный язык и часы. Любое нарушение исключает профиль. Счётчики причин могут пересекаться и не складываются как число людей.

Для max_hours=null длительность присутствия неприменима, поэтому фильтр часов не исключает этот профиль. Дата проверяется внутри известного календаря включительно; отсутствие записей вне окна не трактуется как доступность.

## Ранжирование

Ключ сортировки — последовательность:

1. Число разных тематических основ слов выбранного формата в description, по убыванию.
2. Число разных тематических основ слов выбранной категории в description, по убыванию.
3. Начальная цена, по возрастанию.
4. Стабильный id, по возрастанию.

Точные словари EVENT_STEMS и CATEGORY_STEMS находятся в backend/matching.py. Каждая основа учитывается один раз, повторение рекламного слова не увеличивает её вес. Регистр и ё нормализуются для сопоставления. Это прозрачное лексическое соответствие, не обученная семантическая модель и не рейтинг качества. Ограничение подхода — словари могут не покрывать все синонимы. Существующие ограничения всегда применяются раньше ранжирования.

При одинаковых профилях и запросе результат не зависит от порядка CSV, случайности, сегодняшнего дня или внешней модели. Возвращаются первые min(3, eligible_count). Frontend сохраняет этот порядок.

## Объяснения и сравнение

Каждое объяснение содержит факты соответствия городу, формату, календарю, начальной цене, а при запросе — языку и часам, а также дословный содержательный фрагмент description. Дополнительные поля карточки дают UI возможность сравнить языки, max_hours и описание. Не добавляются рейтинг, отзывы, подтверждённое качество или несуществующий опыт. synthetic/city_imputed/price_imputed и source показывают происхождение данных.

Цена «от» сравнивается с бюджетом, но не является обещанием итоговой стоимости. Отсутствие даты в календаре говорит только о выданных данных, не о подтверждённой реальной брони. Текущий explanation_mode=deterministic; вызовов LLM нет.

## Проверяемые альтернативы

Для no_matches сервер сначала ищет ближайшую другую дату в окне календаря, на которой выполнены все остальные условия. При равном расстоянии берётся более ранняя. Отдельно ищется минимальная начальная цена профиля, удовлетворяющего всем ограничениям кроме бюджета. Если цена выше исходного бюджета, можно предложить увеличить только его.

Каждый совет снова проверяется теми же фильтрами и содержит полный новый запрос и точный eligible_count. Советов не бывает для отсутствующей в городе категории или если нужны сразу два изменения. Применение — только после нажатия пользователя. Рекурсивного поиска советов нет.

## Границы приложения

API и frontend обслуживаются одним процессом. Только frontend разрешён для static, корень репозитория и data не раздаются. Никаких внешних API, DB, платных аккаунтов и обязательных env-переменных нет. Frontend из dev-zoro получает справочники через /api/meta и отправляет запросы в /api/recommendations. HTML/CSS/JavaScript без сборки и внешних runtime-зависимостей обслуживаются тем же процессом.

Источники архитектурных API: [FastAPI exceptions](https://fastapi.tiangolo.com/tutorial/handling-errors/), [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/), [Pydantic strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/). Правила кейса — docs/CASE_REQUIREMENTS.md.
