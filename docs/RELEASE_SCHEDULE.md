## Порядок каждого цикла

1. Делать полезные изменения в своей зоне. За 15 минут до срока перестать расширять объём; к указанному времени начала проверки подготовить содержательный commit/push личной ветки и точный SHA. API-контракт не менять молча, файлы Ilyas не редактировать.
2. Зафиксировать актуальные remote main, integration и готовые SHA участников. Ilyas может продолжать работу независимо; для checkpoint использовать уже готовый согласованный SHA. Рабочая личная ветка остаётся dev-dinmukhammed.
3. В отдельном candidate объединить актуальную общую историю и выбранные части обычными merge. Candidate должен сохранять историю и main, и integration. Если main содержит новые чужие коммиты, включить их и проверить; force/reset/rebase не применять.
4. Проверить затронутые части и живой запуск UI + API из candidate. Использовать настоящий CSV и правильный процесс/порт. Проверить точный runtime-код, который будет опубликован; старый запущенный сервер не доказывает новый код. Записать SHA, команды, реальные результаты и время в docs/integration/.
5. Пока остаётся запас до срока, повторно fetch main/integration. Если общая база сдвинулась, учесть новые изменения и повторить нужные проверки. Опубликовать обычным push проверенный SHA в integration и main. Допустим atomic push обеих веток, когда сервер поддерживает его; при любом отказе не форсировать и не считать действие успешным.
6. Сверить remote SHA обеих веток и предков выбранных частей. На чистой dev-dinmukhammed получить общую версию обычным merge и опубликовать личную ветку. Ilyas синхронизирует свою ветку сам. Сообщить пользователю время, SHA, работающий результат и следующий срок.

Если крупная правка не готова, включить меньший законченный и проверенный результат. Не выкладывать заведомо сломанное приложение и не делать пустые коммиты ради отметки. Если прогресса действительно нет или публикация заблокирована, сразу сообщить факты и сохранить последнюю рабочую main. Сдача формы платформы остаётся отдельным действием капитана.
